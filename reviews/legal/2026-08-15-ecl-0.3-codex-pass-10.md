## CODEX-0.3-020 — Canonical empty-Bundle identifier did not bind canonical components

**Severity:** P1

Codex identified that the `@RP-EMPTY-N` schema branch constrained only the shape of the Schedule reference. It did not require the numeric suffix, License reference, canonical paths, or cryptographic hashes to correspond to the canonical fallback artifacts. The runtime resolver likewise verified only that whatever files a manifest named matched the hashes supplied by that same manifest. A manifest could therefore borrow a canonical-looking fallback Bundle identifier while substituting unrelated License or Schedule components.

### Candidate resolution

Resolved by commits `222e1ecc7c18c539c9eb6b7b8d28f8045ae61e83`, `e22fe1875dd185526648c2af186c995b0462716f`, and `53bce179a249c9bf1bb2ae50b6de9862a24e1507`:

- `schemas/bundle.schema.json` no longer accepts generic `@RP-EMPTY-N` Bundles. The only currently recognized empty fallback is `ECL-0.3-DRAFT@RP-EMPTY-1`.
- For that Bundle the schema pins `operative=false`, exact License ref/path/SHA-256, and exact Schedule ref/path/SHA-256.
- `tools/ecl_resolve.py` now contains an explicit canonical-empty-Bundle registry and rejects every unregistered `@RP-EMPTY-N` identifier.
- Runtime validation compares the complete License and Schedule component identities against that canonical registry before ordinary file/hash validation.
- `tests/test_empty_fallback_bundle.py` now attacks the suffix, License ref/path/hash, Schedule ref/path/hash, and operative flag at both schema and runtime layers, and verifies that an unregistered empty identifier is rejected.

This deliberately makes future empty fallback Bundles opt-in: a new `@RP-EMPTY-N` identity requires an explicit schema/tooling change that pins its exact canonical components rather than becoming valid through identifier syntax alone.
