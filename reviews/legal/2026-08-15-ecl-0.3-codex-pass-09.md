## CODEX-0.3-018 — Version labels were still accepted instead of an exact License artifact

**Severity:** P1 / candidate BLOCKER

**Attack:** Section 4 allowed the fallback when the exact ECL License `artifact or version` was objectively identifiable. A bare label such as `ECL 0.3` can correspond to more than one draft artifact and cannot by itself determine a SHA-256, so downstream grants and termination notices could still lack deterministic Bundle identity.

**Resolution in candidate (`90635f2ec5`):**

- the fallback now requires the **exact ECL License artifact and its SHA-256** to be objectively establishable;
- a version label, branch name, channel name, filename, or other mutable/non-content-addressed label alone is expressly insufficient;
- the fallback Bundle is defined only by the exact License artifact/hash plus the Canonical Empty Schedule artifact/hash; and
- if the exact License artifact/hash cannot be established, the fallback does not manufacture a Bundle or permit a later, mutable, merely version-labelled, or guessed substitute.

**Status:** resolved in drafting; qualified review remains required under LAR-03/LAR-08/LAR-10 and #209/#210.

## CODEX-0.3-019 — Fallback Bundle was not representable by canonical schema/resolver tooling

**Severity:** P1 / candidate BLOCKER

**Attack:** The prose defined the fallback by a pair of component hashes, while `schemas/bundle.schema.json` accepted only date-shaped Bundle identifiers and `tools/ecl_resolve.py` resolved only manifests under `releases/bundles/<bundle>.json`. A recipient could therefore know both hashes but could not validate, pin, or render that state using the repository's canonical Bundle tooling.

**Resolution in candidate (`90635f2ec5`):**

- added immutable License snapshot `versions/licenses/ECL-0.3-DRAFT.md`;
- added canonical manifest `releases/bundles/ECL-0.3-DRAFT@RP-EMPTY-1.json`;
- the manifest pins License SHA-256 `347a39d2e0b2a0df5bbe6c8b4bb0cc97b34f4866061d6be8522fe5f5578eb50d` and Schedule SHA-256 `e12a6ffc03aa0be24a9f61d0d325bc8c06bb9c870416a72fcac0bfd968025aa2`;
- extended `schemas/bundle.schema.json` to admit `@RP-EMPTY-N` Bundle identities while requiring an `ECL-RP-EMPTY-N` Schedule reference for that form;
- intentionally did **not** add a second resolver mode: the fallback is a normal manifest and is resolved through the existing `resolve_pinned()` path; and
- added `tests/test_empty_fallback_bundle.py`, which validates the actual manifest against the Bundle schema, rejects it as stable without `--allow-draft`, resolves it in explicit draft mode, verifies both on-disk SHA-256 values, and renders a lock carrying the canonical Bundle identity.

The first CI unit-test execution on `90635f2ec5` passed these checks.

**Status:** resolved as an internal identity/tooling inconsistency; qualified review remains required under LAR-03/LAR-08/LAR-10 and #209/#210.
