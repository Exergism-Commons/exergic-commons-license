## CODEX-0.3-042 — P2 — repository-root / package-style import shadowing remained possible

Codex identified that the pass-23 bootstrap removed only the exact `tools/` script directory from `sys.path`. If the repository root remained searchable — for example through `PYTHONPATH` or `python -m tools.render_schedule` — root-level modules/packages such as `argparse.py`, `pathlib.py`, or `yaml/` could still participate in import resolution. The post-import origin check was too late to prevent already-executed shadow code and covered only a subset of imports.

### Resolution

The executable Schedule renderer now fails closed unless it is launched as:

```text
python -I -S tools/render_schedule.py ...
```

The bootstrap imports only built-in `sys` before enforcing this gate. `-I` removes cwd, `PYTHONPATH`, and user-site influence; `-S` prevents `site`, `.pth`, and `sitecustomize` processing. The bootstrap then retains only interpreter-owned import roots and adds exactly the interpreter's own `site-packages` directory so the separately pinned PyYAML 6.0.3 dependency remains available. Non-isolated direct execution, isolated execution without `-S`, and package/module-style invocation are rejected before the implementation resolves shadowable imports.

Internal Schedule regression modules may import the bootstrap only from an already isolated (`-I`) interpreter. Both Schedule workflows now run their regression/checker/coverage Python under `-I`, run the renderer itself under `-I -S`, and include the pass-24 regression file in path triggers. Pass-24 regressions exercise non-isolated failure, missing-`-S` failure, package-style failure, and a successful isolated run while root-level `argparse.py`/`yaml/` shadows and `PYTHONPATH=<repo>` are present.

The compatibility-evidence control set continues to bind both `tools/render_schedule.py` and `tools/render_schedule_impl.py` plus `tools/schedule-requirements.txt`. Any bootstrap or implementation change therefore invalidates old completed evidence.
