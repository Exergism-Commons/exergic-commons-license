## CODEX-0.3-038 — P2 — Restrict RFC 3339 timestamp digits to ASCII

### Finding

The `reviewed_at` RFC 3339 grammar used Python regex `\d` in clock, offset and fractional-second positions. Python treats `\d` as Unicode-aware, so quoted strings containing non-ASCII decimal digits such as `2026-08-15T0١:0٢:0٣Z` or `2026-08-15T00:00:00+0١:0٢` could pass the lexical expression. Because only the date component was subsequently parsed with `date.fromisoformat()`, those confusable clock/offset digits could authorize a `complete` compatibility record despite not satisfying the documented ASCII RFC 3339 lexical contract.

### Disposition

Fixed. The ISO-date and RFC 3339 regular expressions now use explicit ASCII `[0-9]` classes throughout date, clock, offset and fractional-second fields. No Unicode-aware digit class remains in the accepted timestamp grammar.

Pass-22 regressions reproduce the two Codex examples plus a non-ASCII fractional-second digit and require rejection, while preserving accepted ASCII date/time/offset/fraction forms.

## CODEX-0.3-039 — P2 — Bind the YAML parser version used by compatibility review

### Finding

The content-addressed compatibility evidence bound the renderer source and repository inputs, but the renderer's semantics also depend materially on PyYAML: `yaml.compose()` constructs the node graph used for duplicate/key/tag/alias checks and `yaml.safe_load()` constructs values used by clause selection and evidence validation. Both Schedule workflows installed unversioned `PyYAML`, so a future parser/constructor change could alter behavior while old evidence still matched every repository-file hash.

### Disposition

Fixed without introducing a broader environment-lock system than the demonstrated dependency requires.

- `tools/schedule-requirements.txt` pins `PyYAML==6.0.3` exactly. This is the same PyYAML release used by the last green pass-21 Schedule workflow environment, not an arbitrary semantic upgrade.
- `tools/render_schedule.py` verifies at runtime that the requirements file has the expected exact pin and that the imported `yaml.__version__` is `6.0.3`.
- The requirements file is included in `schedule_renderer_control_paths()` and therefore in the exact path + SHA-256 compatibility-evidence input set. Changing the parser pin invalidates old `complete` evidence.
- Both Schedule workflows install from that pinned requirements file, trigger when it changes, and execute pass-22 regressions.

The workflows already constrain the interpreter family to Python 3.12. Pass 22 did not add an exact CPython patch/OS/runner-image lock because no separate material bypass was demonstrated for those dimensions. The proven parser dependency is now fixed and evidence-bound.

## CODEX-0.3-040 — P2 — Validate component identity field types before reserved-set lookup

### Finding

For an ordinary Bundle, `_uses_reserved_fallback_identity()` performed set-membership tests directly on `ref`, `path` and `sha256`. A schema-invalid manifest containing an unhashable value such as `"ref": []` or `"path": {}` therefore raised an uncaught `TypeError` before normal component validation. The CLI exception boundary does not treat `TypeError` as the documented malformed-input validation path.

### Disposition

Fixed. Before any reserved-fallback namespace lookup, each present Bundle component identity dimension (`ref`, `path`, `sha256`) is required to be a non-empty string. Malformed values now raise a deterministic `ValueError` and cannot reach Python set membership.

Regression coverage attacks both License and Schedule slots across all three identity dimensions and includes an explicit assertion that malformed input never escapes as `TypeError`.
