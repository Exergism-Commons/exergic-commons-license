## CODEX-0.3-026 — P2 — Bind review IDs to immutable compatibility evidence

**Finding.** Pass 14 bound the mutable compatibility pointer to exact target-License and source hashes, but a future edit could refresh those claims while retaining an old free-form `review_id`. `validate_compatibility_review()` did not independently resolve that ID to evidence showing which bytes the review actually covered.

**Disposition: resolved in candidate.**

- `registry/schedule-license-compatibility.yml` is now schema v3 and is only a mutable state/pointer document.
- A `complete` state may not carry legacy top-level `review_id` or `sources` claims.
- It must reference `review_evidence.id` plus the exact path `reviews/schedule-compatibility/<id>.yml`.
- `<id>` must be a lowercase SHA-256 and must equal the SHA-256 of the evidence file's own bytes.
- The evidence file independently binds the exact target License label/path/hash and the entire renderer-consumed source path/hash set and records reviewer, review time and `conclusion: compatible`.
- The renderer rejects missing evidence, path/ID disagreement, evidence-byte tampering, target-License mismatch, stale/missing/extra/duplicate source bindings, and any attempt to reuse old evidence after refreshing the target License pointer.
- Regression coverage constructs valid synthetic content-addressed evidence, tampers with it under the same ID, and attempts to reuse old evidence after moving the mutable pointer to new License bytes.

This content-addressing is repository integrity evidence for the Schedule compatibility mechanism; it is not a claim of qualified legal review.

## CODEX-0.3-027 — P2 — Permit workflows to accept completed compatibility reviews

**Finding.** Both Schedule workflows hard-coded the repository's current `pending` output. A legitimate future `complete` state would make the renderer emit `Intended compatibility` and omit the pending markers, causing CI to reject the very successful state supported by the renderer.

**Disposition: resolved in candidate.**

- Added `tools/check_schedule_compatibility_output.py` to validate rendered compatibility text semantically against `registry/schedule-license-compatibility.yml`.
- For `pending`, it requires the target/exact-artifact/pending markers and rejects a completed compatibility claim.
- For `complete`, it requires the intended-compatibility and immutable-evidence completion markers and rejects stale pending markers.
- Both Schedule workflows now call that semantic checker rather than grep for a permanently pending state.
- Both workflows also trigger on `reviews/schedule-compatibility/**` and on the semantic checker itself, in addition to the License and registry inputs.
- Regression coverage exercises both pending and complete rendered states and asserts that neither workflow retains the old pending-only grep logic.
